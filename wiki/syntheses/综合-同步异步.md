# 综合：同步与异步

**一句话总览**：**同步 = 发起操作后必须等它完成才能继续；异步 = 发起后立即返回，完成时由系统"回头叫你"。** 两者是同一件事的两种组织方式，区别只在"**谁等谁**"。放到函数调用上：**同步调用 = 函数返回时活已经干完；异步调用 = 函数只负责"提交任务"就返回，真正的活由系统在别处执行，干完回调通知你。**

## 两个层面：操作级与函数调用级

| 层面 | 同步 | 异步 |
| --- | --- | --- |
| **操作级** | 操作完成才返回控制权 | 操作立即返回，完成时通知 |
| **函数调用级** | 被调函数执行完才返回 | 被调函数只"提交任务"即返回，实际工作稍后执行 |

## 同步调用 vs 异步调用一个函数

**同步调用**：
```c
result = sensor_read();       // 阻塞直到读到数据
process(result);              // 此时 result 已可用，直接处理
```
- 调用线程**卡在函数里**直到函数返回；
- 结果**通过返回值**直接拿到；
- 流程**线性直白**：下一行执行时，上一行已完成。

**异步调用**：
```c
sensor_read_async(on_data);   // 立即返回！数据还没读
// 下一行立即执行，此时 sensor_read 可能刚开始甚至没开始
other_work();                 // 调用线程被释放，去做别的
...
// 数据就绪时，系统调用 on_data(result) 通知你（可能在 ISR / 另一线程）
```
- 调用**立即返回**，不阻塞调用线程；
- 函数实际执行发生在"别处"（[[中断上半部与下半部]] 的 ISR、RTOS 任务、独立线程）；
- 结果**通过回调 / 事件 / 轮询**获得，而非返回值；
- 需要额外的同步机制（[[消息队列]] / [[信号量]]）在完成时通知调用方。

## 核心对比

| 维度 | 同步 | 异步 |
| --- | --- | --- |
| 调用后行为 | 阻塞等待完成 | 立即返回 |
| 结果获取 | 返回值直接拿 | 回调 / 事件 / 轮询 |
| 调用线程 | 被占用 | **被释放**（可做别的事） |
| 流程 | 线性、直白、易调试 | 事件驱动、隐晦、状态管理复杂 |
| 吞吐 / 并发 | 低（串行等待） | 高（可重叠执行） |
| 资源代价 | 线程被占（多并发需多线程） | 需额外的回调/队列/状态机基础设施 |

## 嵌入式里的典型体现

1. **MQTT 客户端两套 API**（[[同步异步客户端API]]）：Paho C 的 `MQTTClient`（同步，`waitForCompletion` 阻塞到 QoS 确认）vs `MQTTAsync`（异步，连接/消息事件回调）。选择维度：简单性 → 同步；高并发 / 单线程嵌入式 → 异步。
2. **ISR 与任务**（[[中断上半部与下半部]]）：硬件事件天然异步——ISR 立即打断，只做必要操作，重活经 [[消息队列]] 交给任务；这正是"异步 + 解耦"的模型。
3. **回调的本质**（[[综合-回调函数并发并行]]）：异步的"完成通知"靠回调实现，回调是**并发**机制——它不创建新的执行单元，只是让 CPU 在代码段之间切换。

## 如何选

| 场景 | 选 |
| --- | --- |
| 流程简单、调试友好、低频操作 | **同步** |
| 单线程嵌入式、不能阻塞、要高吞吐 | **异步**（回调 + 队列） |
| 需要确定性确认（如 QoS 投递成功） | 同步 `waitForCompletion` 或异步投递回调 |
| I/O 等待（网络/外设慢） | **异步**（等待期间释放 CPU，呼应 [[综合-降低cpu占用率]]） |

## 一句话记忆

> **同步是"叫了外卖坐在家等"，异步是"叫了外卖该干嘛干嘛，到了电话叫你"**——同步等结果、异步等通知；同步占线程、异步放线程。
