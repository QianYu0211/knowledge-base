# 综合：FreeRTOS 任务的内存分配

**一句话总览**：一次 `xTaskCreate()` 在 `ucHeap` 上分配的是"**一个任务对象的内存包**"——内部由 **TCB（任务控制块，任务的档案袋）+ 任务栈（任务的私人更衣室）** 两块构成。围绕"内存"有四问：**分配什么**（TCB + 任务栈各装什么）、**从哪来**（`ucHeap` 静态数组堆）、**分配多少**（三要素估算 + 实测校准）、**怎么监控**（堆水位 + 栈水位）。看懂这四问，FreeRTOS 的内存模型就完整了。

## 第一问：分配什么——内存包的解剖

### 0. 分配的本质：内核对象，而非裸字节

[[FreeRTOS堆内存管理]] 明确：任务、队列、信号量等**内核对象**创建时统一从静态数组 `ucHeap[]` 经 `pvPortMalloc()` 分配。所以"分配什么"的第一层答案是——**分配一个结构化的任务对象**，不是一段无意义的内存。

### 1. 块一：TCB（`tskTCB`）——任务的"档案袋"

[[FreeRTOS]] 给出 TCB 的身份与关键字段：

> 每个任务都有独立的栈与任务控制块 TCB（`tskTCB`），TCB 首位是 `pxTopOfStack`（栈顶指针，保存任务寄存器上下文的入口），`xStateListItem` 状态牌嵌入 TCB，任务状态改变时只需把挂钩从一张链表换到另一张，零内存开销。

| 字段 | 装什么 | 用途 |
| --- | --- | --- |
| `pxTopOfStack` | **栈顶指针**（TCB 首位） | 任务寄存器上下文的入口，切换时据此存取栈 |
| `xStateListItem` | **状态牌**（嵌入 TCB） | 挂到就绪/延迟链表，换列表零内存开销（[[任务调度]]） |
| `uxPriority` | 优先级值 | 抢占判断（`pxTCB->uxPriority`，[[任务调度]]） |
| `pvOwner` | 链表节点"认主"指针 | 经 `pvOwner` 找到该节点所属的任务（[[任务调度]]） |

### 2. 块二：任务栈——任务的"私人更衣室"

任务栈不是空白内存，它有三种身份、装三样不同内容（[[任务上下文切换]] + [[任务栈大小估算]]）：

| 帧 | 何时写入 | 装什么 |
| --- | --- | --- |
| **初始帧** | 创建时预置 | 任务启动的初始上下文，首个任务靠 SVC 异常加载（[[启动流程]]） |
| **运行帧** | 执行时增长 | 局部变量、函数嵌套调用的**返回地址 + 保存寄存器**（Cortex-M 硬件自动压栈）、函数参数 |
| **切换帧** | 切换时写入 | 上下文切换保存的**通用寄存器 R4-R11、LR、PSP**（部分硬件自动压栈、部分软件保存），入口记在 `pxTopOfStack` |

配合 Cortex-M **双栈机制**：MSP（主栈，中断/内核用）与 PSP（进程栈，**每个任务独立**）——任务切换时只需"把 PSP 指到目标任务栈顶"即可换栈运行。

```
ucHeap（pvPortMalloc 分配）
┌──────────────────────────────────────────────┐
│  一个任务对象的内存包                          │
│  ┌──────────────────┬───────────────────────┐ │
│  │  TCB（档案袋）     │  任务栈（更衣室）        │ │
│  │  pxTopOfStack     │  初始帧（启动上下文）    │ │
│  │  xStateListItem   │  运行帧（局部变量/调用）  │ │
│  │  uxPriority       │  切换帧（R4-R11/LR/PSP）│ │
│  │  pvOwner          │  （向下增长）            │ │
│  └──────────────────┴───────────────────────┘ │
└──────────────────────────────────────────────┘
```

### 3. 两块怎么协同：为什么这么分配

任务切换的七步流程（[[任务上下文切换]]）正好解释这个分工：

```
SysTick 报时 → 调度器决策 → PendSV 保存旧任务寄存器入栈 → 更新 pxTopOfStack
   → vTaskSwitchContext 选新任务 → 从新任务栈恢复寄存器、切 PSP → 跳转运行
```

- **TCB 负责"我是谁 + 挂在哪个队列"**——状态牌嵌 TCB 让换链表零开销；
- **任务栈负责"我上次干到哪 + 我的局部数据"**——`pxTopOfStack` 是这两块的接缝，TCB 通过它读写栈。

## 第二问：从哪来——`ucHeap` 静态数组堆

[[FreeRTOS堆内存管理]] 的关键结论：

- FreeRTOS **不依赖 C 库的 malloc**，用静态数组 `ucHeap[configTOTAL_HEAP_SIZE]` 编译期划在 SRAM `.bss` 段；
- 分配入口统一是 `pvPortMalloc()`/`vPortFree()`；
- **与启动文件 `Heap_Size` 是两套独立空间**——C 库 `malloc()` 用启动文件 HEAP 区，`pvPortMalloc()` 用 `ucHeap`，互不相干。

## 第三问：分配多少——三要素估算 + 最小约束 + 实测校准

[[任务栈大小估算]] 给栈大小的**静态三要素**：

1. **任务局部变量占用**——如 `char pcWriteBuffer[200]` 直接占 200 字节栈；
2. **最差函数嵌套深度**——调用链每层返回地址 + 保存寄存器（Cortex-M 硬件自动压栈）；
3. **函数传参数量与大小**——大结构体传值比传指针更耗栈。

**最小栈约束**：

> FreeRTOS 单个任务**最少需要 128 字**（`configMINIMAL_STACK_SIZE` = `(uint16_t)128`）……小于该值会导致任务无法创建或运行时崩溃。

估算给出初值，再用 [[栈水位监控]] 实测校准：最恶劣路径下水位接近 0 就加大、过高就调小，得到"够用 + 20~30% 余量"。

## 第四问：怎么监控——两套水位 API

| 维度 | 堆水位（[[FreeRTOS堆内存管理]]） | 栈水位（[[栈水位监控]]） |
| --- | --- | --- |
| 总大小 | `configTOTAL_HEAP_SIZE` | `xTaskCreate()` 栈大小参数 |
| 当前剩余 | `xPortGetFreeHeapSize()` | —（栈水位是历史最低） |
| 历史最低 | `xPortGetMinimumEverFreeHeapSize()` | `uxTaskGetStackHighWaterMark()`（**单位是字×4**） |
| 全貌 | — | `vTaskList()` 全任务信息表 |

## 三个常见坑

- **内存泄漏**：`pvPortMalloc()` 后不 `vPortFree()`，堆只减不增，创建任务/队列失败——看历史最低堆水位是否逼近 0（[[FreeRTOS堆内存管理]]）。
- **碎片化盲区**：堆水位 API"只统计剩余字节数，**不反映碎片化**"——总量够但分配失败，很可能是碎片。
- **栈溢出**：栈不足破坏 [[任务上下文切换]]，导致不可预期崩溃；`uxTaskGetStackHighWaterMark()` 返回值**单位是字，需×4 得字节**，是最常见误用点（[[栈水位监控]]）。

## 通用知识补充（wiki 未详述，标注说明）

以下为 FreeRTOS 通用事实，当前知识库页面未覆盖，暂以补充形式记录：

- 真实 FreeRTOS 中 `xTaskCreate` 通常**一次 `pvPortMalloc` 分配一整块连续内存**，低地址放 TCB、高地址放栈；
- TCB 内还随配置宏（`configUSE_*`）包含任务名缓冲、任务本地存储指针数组、互斥持有者字段等。
