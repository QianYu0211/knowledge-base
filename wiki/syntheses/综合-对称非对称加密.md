# 综合：对称加密与非对称加密

**一句话总览**：**对称加密用"同一把钥匙"加解密（快但分发难）；非对称加密用"公钥+私钥对"（解决分发但慢）。** 二者是互补的对偶方案——现实中几乎总是**组合使用**（混合加密 + 数字签名），而不是二选一。

## 核心区别表

| 维度 | [[对称加密]] | [[非对称加密]] |
| --- | --- | --- |
| **密钥** | 加解密**同一密钥** | **公钥 + 私钥**一对 |
| **速度** | **极快**，开销小（数据面主力） | **非常慢**，不适合大量数据 |
| **核心优势** | 高速加解密 | **解决密钥分发难题** |
| **核心劣势** | **密钥分发困难**（如何安全送达） | 慢 |
| **代表算法** | [[AES]]、DES、SM4 | RSA、ECC |
| **比喻** | 一把普通钥匙（开锁上锁都用它） | 公开邮箱（谁都能投信，只有钥匙能开箱） |
| **服务目标** | **保密性** | **密钥交换 + 认证/不可否认**（[[信息安全目标]]） |

## 各自详解

**对称加密**（[[对称加密]]）：

> 加密和解密使用**同一个密钥**。核心优势是速度快、计算开销小，适合对大量数据高速加解密；核心劣势是**密钥分发困难**——如何安全地把同一把钥匙送到通信双方手中是巨大挑战。

**非对称加密**（[[非对称加密]]）：

> 使用一对密钥——**公钥**（公开）与**私钥**（保密）。用公钥加密的内容只能由私钥解开（反之亦然），完美解决 [[对称加密]] 的密钥分发难题，但速度非常慢，不适合加密大量数据。

## 为什么互补：一个解决"分发"，一个解决"速度"

对称加密快但"钥匙怎么安全送达"；非对称加密钥匙随便给（公钥公开）但慢。**组合**是必然：

```
对称加密：快，但钥匙怎么送到对方手上？
非对称加密：钥匙随便给（公钥公开），但慢得没法加密大数据
        ↓ 组合
混合加密：用非对称安全传"钥匙"，再用对称高速通信
```

**组合方案一：混合加密**（HTTPS 典型流程，服务**保密性**，[[非对称加密]]）：
1. 浏览器拿服务器公钥；
2. 生成临时随机**对称密钥**（"密码本"）；
3. 用服务器公钥加密"密码本"发给服务器；
4. 服务器用私钥解密得到对称密钥；
5. 此后双方用对称密钥（如 [[AES]]）高速通信。

**组合方案二：数字签名**（服务**认证性 + 不可否认性**）：
1. 发布方对软件包算哈希；
2. 用**私钥**对哈希签名并发布；
3. 用户用**公钥**验签 + 自己重算哈希；
4. 一致 → 来源可信且内容完整（[[哈希函数]] + 非对称）。

## 在四大目标中的分工（[[信息安全目标]]）

| 目标 | 用谁 |
| --- | --- |
| **保密性** | 对称加密（[[AES]]） |
| **完整性** | [[哈希函数]] / MAC |
| **认证性** | 数字签名（非对称） |
| **不可否认性** | 数字签名（非对称） |

## 嵌入式实战呼应

参考工程 OTA 正是这套体系的完整案例：**密钥出厂写入 [[加密芯片]]（Keros），固件用 [[AES]]（对称）加密密文，量产方案用 OPT Flash 公钥签名验证**（非对称）——对称管保密性、非对称管认证性（[[固件保护]] / [[OTA升级]]）。

## 一句话记忆

> **对称 = 一把钥匙快但难送；非对称 = 两把钥匙好分但慢**——所以现实中"非对称递钥匙、对称搬数据"（HTTPS），"私钥签名、公钥验签"（数字签名）。
