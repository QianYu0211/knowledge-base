## 定义

GATT（Generic Attribute Profile，通用属性协议）定义了 BLE 设备之间**数据的组织与交互方式**：设备包含若干**服务（Service）**，服务包含若干**特性（Characteristic）**，特性是数据交互的最小单元，每个服务/特性都由 **UUID** 唯一标识。手机等主机通过读写特性、订阅通知来与设备交换数据。

## 关键信息

- **UUID 与 16-bit 简写**：UUID 是 128-bit 通用唯一标识符；蓝牙联盟定义了基地址 `0x0000xxxx-0000-1000-8000-00805F9B34FB`，允许在基地址基础上使用 **16-bit UUID** 简写（如 `0x2A37` ⇄ 完整 128-bit），减少传输开销。
- **结构层级**：设备（Device）→ 服务（Service）→ 特性（Characteristic）；一个服务聚合一组相关数据，特性则携带具体数据值与属性权限。
- **五种数据交互方式**：
  - **Read**：主机主动读取特性值；
  - **Write**：主机写入特性值（需设备端确认）；
  - **Write Without Response**：主机写入但无需确认；
  - **Notify**：设备主动推送，主机无需回复（最常用）；
  - **Indication**：设备主动推送且要求主机确认。
- **创建服务/特性的四步**（MicroPython）：① 创建 UUID → ② 用 UUID 创建特性并设置权限（`FLAG_READ/FLAG_WRITE/FLAG_NOTIFY`）→ ③ 将特性放入服务集合 → ④ `gatts_register_services()` 注册到 GATT 协议栈。
- **权限决定能力**：特性的交互方式由创建时的权限标志决定——未开启 Write 权限的特性无法被主机写入，未开启 Notify 则无法主动推送。
- **蓝牙联盟已定义的常用 16-bit UUID**（可直接复用）：
  - 电池电量服务 `0x180F` / 电量特性 `0x2A19`（1 字节，单位百分比）；
  - 环境传感器服务 `0x181A` / 温度特性 `0x2A6E` / 湿度特性 `0x2A6F`（各 2 字节，**低字节在前**，温度单位 0.01°C、湿度单位 0.01%）。
- **与上层 Profile 的关系**：[[HID协议]]、[[蓝牙MIDI协议]] 等 Profile 通过规定特定服务/特性的 UUID 与数据格式，在 GATT 之上实现标准化的设备行为。
- **Service vs Characteristic 的工程理解**：Service 是"功能分组/模块"，解决**分类**问题；Characteristic 是分组下的"具体字段/控制点"，解决**具体数据怎么读写**。例：一个"设备监测服务"下挂温度、湿度、振动 RMS、电池电压、设备运行状态等特性。
- **ATT 映射**：主机扫描到从机后会枚举其整个 **ATT 属性表**，据此推算出 GATT 结构（面试中常将 ATT 类比为"数组"；技术上 ATT 是属性表——每个属性含句柄、类型 UUID、权限与值）。
- **自定义 GATT Profile 的动机**：当业务数据（如工业监测的振动/温湿度/电压电流/状态/控制）不属于标准健康或通用外设 Profile 时，硬套标准 Profile 不合适；自定义 Profile 字段含义清楚，后续加传感器/状态位易扩展。
- **数据标准化编码**：统一"类型（Type）-长度（Length）-数据内容"的编码格式，保证手机/网关/上位机多端按同一规则解析，降低协议维护成本。
- **Notify/Read/Write 的工程分工**：Notify 偏**主动推送**（实时性强、状态变化/告警/关键监测值，免轮询）；Read 偏**主动查询**（温湿度/电压/状态随时读）；Write 偏**控制**（修改工作模式、下发参数、切换上报策略）。
