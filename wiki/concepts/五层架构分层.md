## 定义

五层架构分层是一种嵌入式软件架构方法，把代码按 **App → Service → Platform → Impl → Vendor** 五层组织，让每一层只依赖它的下层。目的是**隔离变化**——换屏幕、换 IMU、调算法、改通信协议时，改动只落在对应的层，不扩散到整个工程。

> 一句话：**App 只描述产品要干什么，不关心硬件怎么干**——把"变化"关进每一层的笼子里。

## 为什么先分层

项目变大后必然面临的变化：屏幕/IMU 换型号、心率/电量算法调整、低功耗策略升级、FreeRTOS 任务重构、BLE 通信协议调整。如果 App 层直接调用 HAL，**每个变化都会扩散到整个工程**——分层让每个变化有明确的落点，驱动写错位置后也便于迁移。

## 五层职责

| 层 | 职责 | 口诀 |
| --- | --- | --- |
| **App** | 产品业务流程（开机、页面切换、交互、OTA 入口） | App 只描述产品要干什么，不关心硬件怎么干 |
| **Service** | 可复用系统能力（battery/sensor/display/power/log/ota/ble/watchdog/storage/diagnosis） | Service 把底层能力组织成可复用的系统能力 |
| **Platform** | 平台抽象层：统一接口 / 错误码 / 数据结构 / ops 函数指针 / ctx 上下文 | Platform 只定义能力，不绑定具体芯片 |
| **Impl** | 把 Platform 接口落到具体平台（STM32 GPIO/I2C/SPI、FreeRTOS OS 接口、LVGL 显示适配） | Impl 是 Platform 和 Vendor 之间的适配层 |
| **Vendor** | 厂家/第三方底座（STM32 HAL、CMSIS、CubeMX、FreeRTOS/LVGL/FatFS 源码、原厂 SDK） | Vendor 只提供底座能力，不理解产品业务 |

调用链实例（App 点亮一个 LED）：

```
app_main() → service_led_set() → platform_gpio_write()
           → impl_stm32_gpio_write() → HAL_GPIO_WritePin()
```

## 依赖方向规则

**正确**：`App → Service → Platform → Impl → Vendor`

**禁止反向**：
- **Impl 不能调用 Service**（下层不知道上层存在）；
- **Platform 不能绑定具体芯片**（不能 include `stm32f4xx_hal.h`）；
- **App 不能直接调用 HAL**（换芯片/驱动方式会波及 App）；
- **Service 不能绕过 Platform 直接调用 Vendor**。

## 常见问题速查

| 问题 | 答案 |
| --- | --- |
| 分层是不是过度设计？ | 不是，为了让项目能继续长大 |
| App 为何不能直接调 HAL？ | HAL 是具体芯片/厂商库，换芯片会影响 App |
| Service vs App？ | App 偏产品流程，Service 偏可复用能力 |
| Platform vs Impl？ | Platform 定标准，Impl 做适配 |
| BSP 放哪？ | 板级资源映射放 Impl/Board，器件级驱动可放 impl_bsp |
| main.c 属于哪层？ | 启动胶水代码，只做启动转发，不写业务逻辑 |
| Impl 能调 Service？ | 不能，下层不要知道上层存在 |
| Vendor 能改吗？ | 尽量不要，通过 Impl 适配 |
| Impl 空函数正常吗？ | 正常，先有骨架再长血肉 |

## 与既有概念的呼应

- 分层思想与 [[协议分层]] 的"语言与扩音器"同源——都是把"变化隔离到层内"；
- **Platform 定接口 + Impl 做适配**，本质是 [[适配器模式]] 的架构级应用（抹平硬件差异）；
- **ops 函数指针 / ctx 对象协议**，是 [[C语言面向对象]] 与 [[函数指针]] 的实践——Platform 用函数指针表定义"能力"，Impl 填充具体实现。
