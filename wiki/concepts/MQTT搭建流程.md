## 定义

「搭建 MQTT 通信网络」看似涉及大量具体步骤，但其本质是一个**与语言、操作系统、Broker 品牌无关的六阶段通用流程**。抽象掉"用哪台机器装 EMQX"、"用 Python 还是 Java"这类实现细节后，任何 MQTT 项目都遵循同一骨架：**规划拓扑 → 部署 Broker → 客户端接入准备 → 实现订阅者 → 实现发布者 → 验证链路**。本页把这一骨架提炼为可复用的方法论。

## 关键信息

### 六阶段通用流程

| 阶段 | 动作 | 通用要点 |
|---|---|---|
| ① 规划通信拓扑 | 确定发布者、Broker、订阅者三种角色，设计主题（Topic）命名 | 明确"谁发什么、谁收什么"；主题是唯一的通信纽带 |
| ② 部署消息代理（Broker） | 选型 → 下载安装包 → 安装 → 启动服务 → 打开管理控制台 | 无论 Mosquitto / EMQX、Windows / Linux，都走"装 → 启 → 验"三步 |
| ③ 客户端接入准备 | 选客户端路径（图形工具或 SDK 库），备好连接参数 | 参数 = Broker 地址（IP:1883）+ 唯一 ClientID + 可选账号密码 |
| ④ 实现订阅者 | 连接部分同发布者 → 注册回调 → 订阅主题 → 保持存活 | **先建订阅者**：监听方先就位，广播一发即收；订阅者必须长驻在线，消息靠回调驱动 |
| ⑤ 实现发布者 | 建客户端对象 → 配置连接 → 连接 Broker → 启动网络循环 → 发布 | 发布本身是一行调用，难点在连接与循环；发布者即发即断亦可 |
| ⑥ 验证全链路 | 先启动订阅者就位 → 运行发布者 → 在订阅端与控制台确认收到 | 跨机器部署即真实组网，Broker 控制台是"X 光机" |

### 阶段细节与关键决策

- **① 拓扑与主题**：先画角色图再动手。主题建议按层级命名（如 `设备ID/数据类型`），与具体业务解耦；订阅者可用通配符订阅一组主题。
- **② Broker 选型与部署**：
  - **选型**：轻量单机选 Eclipse Mosquitto；大规模并发、需可视化控制台选 [[EMQX]]（单台可达亿级连接）。
  - **安装共性**：官方渠道下载平台对应包（Windows zip / Linux 包 / Docker）→ 解压/安装 → 注册为系统服务。
  - **启动共性**：开发环境"服务 + 监控控制台"分别拉起；正式环境一条命令同时启动（如 `emqx start`）。
  - **验证**：浏览器访问管理控制台（EMQX 默认 `IP:18083`，账号 `admin`/`public`）确认 Broker 存活。
- **③ 客户端接入两种路径**：
  - **图形化工具先行**：用 [[MQTTX]] 不写代码验证 Broker 连通性（类比 Navicat 之于 MySQL）。
  - **SDK 落地实现**：按语言引入客户端库（Python `paho-mqtt`、Java `org.eclipse.paho.client.mqttv3`），封装进业务代码。
  - 连接参数是唯一硬性依赖：**Broker 地址 + 端口 1883 + 唯一 ClientID**。
- **④ 订阅者（先建：监听方先就位）**：连接骨架与发布者**完全相同**；随后 ① 写 `on_message` 回调（每收到一条消息触发一次）② 把回调绑定到 client ③ `subscribe(topic)` ④ 启动循环并**保持进程存活**。**先建订阅者符合调试直觉**——如同先开收音机调好频道，广播一发即可收到；订阅者长驻在线、不能断开。
- **⑤ 发布者（后发：语言无关的五步骨架）**：导入库 → 创建 client（带唯一 ClientID）→ `connect(BrokerIP, 1883)` → 启动网络循环 `loop_start()`（独立线程，不阻塞主流程）→ `publish(topic, payload, qos)`。发布者在订阅者就绪后触发即可，可即发即断，也可长连持续发送。
- **⑥ 验证与排障**：Broker 控制台应能看到客户端上线/下线与消息收发计数——这是最可靠的"是否打通"判据。**最常见的失败点**：防火墙未放行 1883 端口（连接回调返回非 0 时优先检查）。

### 跨实现不变量（抽象的核心结论）

1. **Topic 是唯一纽带**：发布与订阅只要主题同名即建立连接，与 IP、端口转发、对端身份无关。
2. **发布者与订阅者 90% 代码相同**：差异只在"publish 一行"与"subscribe + 回调"；故流程把**订阅者排在发布者之前**——监听方先就位，调试时才能当场看到消息到达（见阶段 ④⑤）。
3. **网络循环形态可迁移**：`loop()`（单次）/ `loop_start()`（线程，最常用）/ `loop_forever()`（阻塞），任何语言客户端库均有对应物。
4. **控制台是调试之锚**：无论语言，Broker 的管理界面提供统一的可观测性。
5. **流程不随规模改变**：单机实验、跨机器组网、大规模集群，六阶段骨架一致，只是部署形态与配置复杂度递增。

### 案例印证：Paho C 同步 API 的六步即六阶段

[[Paho]] C 客户端教程的代码骨架——`create → 配置 options → connect → subscribe/publish → 清理`——正是六阶段流程在 C/嵌入式场景的实例化：连接参数（地址 + 端口 + ClientID）是「接入准备」的唯一硬依赖；`messageArrived` 回调是「订阅者」的消费入口；`waitForCompletion` 阻塞确认对应 QoS 投递保证；其示例在 `connect` 后**先 `subscribe` 再 `publish`**，与「先订阅者后发布者」的顺序约定一致。生产实践（唯一 ClientID、TLS、合理 keepAlive、QoS 0 优先）与跨实现不变量完全吻合。这反向验证了抽象的有效性：**换一种语言，骨架不变，只是 API 名词不同**。
