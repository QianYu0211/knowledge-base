## 定义

OTA（Over-The-Air）升级是通过网络（串口/无线）**远程下载并安装新固件**的机制，目标是"无感"——用户最多感知一次普通重启。核心是一个存储在 Flash 中的 **App 标识**接力棒，在 App（准备方）与 [[Bootloader]]（安装方）之间传递控制权与任务指令。

## 关键信息

- **发现升级（CHECK_UPDATE）**：手表连接手机后，监控线程**定期向服务器查询最新版本号**，与本地当前版本对比——**服务器版本高于本地**则判定需要升级，进入 `CHECK_UPDATE` 状态（[[摘要-ota无感升级]] 的 `IDLE → CHECK_UPDATE → DOWNLOADING`）。随后**评估下载条件**（空闲/繁忙/电量/Flash 裕度，见 [[综合-智能手表OTA全流程]] 图1）决定低速/高速下载；量产方案还以"新固件版本须高于现版本"作为防回退的硬指标。
- **App 阶段（后台静默准备）**：
  - 监控线程定期查询服务器，按设备繁忙度决策**低速/高速下载**（降波特率或降线程优先级不抢占主程序）；
  - OTA 线程用**非阻塞 [[YMODEM]]** 下载，接收采用 `中断 + [[DMA双缓冲]]` 黄金组合：DMA 存满 A 后中断切到 B 无缝续收，CPU 把 A 的地址经**消息队列**交给 Flash 线程写入外部 Flash 下载区（A 区）；
  - Ymodem 断点续传保证断网/断电后续传；
  - 更新时机：主动（弹窗）/ 静默（休眠、充电时）；时机成熟 → 置标识"待更新" + 软复位。
- **Bootloader 阶段（多次自动重启安装）**：
  1. 重启①验证 A 区固件（**解密 + [[CRC]] 校验**），失败则放弃更新（避免变砖）；
  2. 重启②A 区搬运到备份区 B 区（断电有完整备份）；
  3. 重启③擦除 App 运行区 → 从 B 区逐块解密校验写入 → 全量 CRC 校验 → 成功置"有效 App"、失败置"无效"；
  4. 最后重启启动**看门狗**后跳转新固件。
- **状态机**：`IDLE → CHECK_UPDATE → DOWNLOADING → VERIFYING → UPDATING → UPDATED`，任一失败转 `ROLLBACK → IDLE`。
- **回滚与防回滚**：写入校验失败 / 启动超时 / 关键功能异常 → 标记当前版本 BAD → 切备份区运行旧版本；同版本连续失败 3 次标记不可用，需用户手动确认重试。
- **安全要点**：固件下载与存储加密（[[AES]]）、完整性校验（[[CRC]]/[[哈希函数]]）、签名认证（防恶意固件），对应 [[信息安全目标]] 四目标。

## 具体项目实现（蓝牙 + 双 Bank 方案）

源自《OTA面试整理》的具体量产方案，硬件拓扑与通用框架对应如下：

- **硬件链路**：手机端/PC 端 → 蓝牙（[[NRF52840]]）→ 主 MCU ↔ [[加密芯片]]（[[I2C]] 通信）；外部 Flash 分 A/B 双区，内部 Flash 存 App 运行区 + 标志位。
- **加密与密钥**：新固件经 [[AES]] 加密为密文，密文末尾携带 MD5 值（具体追加/校验机制见 [[完整性校验方案]]）；密钥与向量出厂前写入 [[加密芯片]]，解密时按需读取。
- **传输**：蓝牙 + [[YMODEM]] 逐帧传输密文到外部 A 区，逐帧 [[CRC]] 校验 + 断帧重传。
- **安装**：A 区完整后写内部 Flash 标志位 → UI 询问用户 → 软复位 [[Bootloader]] → 判读标志位 → A 区密文 1KB/次搬入 SRAM → 读加密芯片密钥解密 → 写入内部 Flash → 计算解密后固件的 MD5 并与明文 MD5 比对 → 通过则写"初步校验通过"标志 → 开启 4S [[看门狗]] → 跳转新 App。
- **确认与备份**：新 App 在 4 秒内执行到末端并写"正常运行"标志 → 再次软复位 → BootLoader 将 A 区密文拷贝到 B 区作为新备份 → 擦除标志位 → 跳转 App，完成升级。
- **回滚与兜底**：MD5 不符或 App 超时 → 回滚 B 区（升级前可正常运行的固件密文）防变砖；上电自检校验 B 区完整性与签名，失败则从当前 App 重新加密备份；极端情况经串口发加急失效指令重传固件。
- **升级前提**：产品价值（有功能提升或 Bug 修复）、环境与设备状态（网络/蓝牙稳定、电量充足、Flash 裕度、空闲期后台升级）、固件加密（OPT Flash 公钥签名认证 + 版本号高于现版本防回退）、用户授权。

## 知识冲突

> 依据项目流程图（App 无感升级流程 / OTA_FlowChart / Bootloader 白板）与源码（`Boot_Manager.c`）校准后的结论：两套描述是**同一系统在不同抽象层级**的呈现，大部分"分歧"实为**阶段或实现细节差异**，已澄清如下。

| 维度 | 通用框架《OTA无感升级流程》 | 具体项目《OTA面试整理》 | 辨析结论（源码/图证实） |
| --- | --- | --- | --- |
| 断点续传 | Ymodem 断点续传，断网/断电后从上次位置继续 | 当前项目**不支持**断点续传 | **不冲突，是阶段不同**：App 下载阶段确有断点续传（App 流程图"优化机制方案"含断点续传）；"不支持"指 Bootloader 安装阶段（A 区搬入内部 Flash）不续传，断电丢弃重传 |
| 备份时机 | 升级中先 A 区搬 B 区，再从 B 区解密安装 | B 区存升级前可运行固件；升级成功后 A 区拷贝 B 区 | 具体项目源码证实**成功后备份**（`APP_AreaAToAreaB` 状态）；通用框架的"先备份再安装"属另一种设计 |
| 校验侧重 | 以 CRC 为主：验证阶段解密+CRC、安装后全量 CRC | 以 MD5 为主：密文尾部附 MD5，解密后比对；CRC 仅传输逐帧 | 具体项目源码证实 **MD5 为主**（`BackToApp` 解密后 MD5 比对）、Ymodem 逐帧 CRC；两套校验工具分工不同 |
| 安装顺序 | 多次重启：验证→备份→安装→看门狗跳转 | 解密直写内部 Flash→MD5→看门狗跳转→成功后再备份 | 具体项目源码证实 **单次解密直写 + CheckAppValid + 置标志复位**，非多次重启逐步安装 |
