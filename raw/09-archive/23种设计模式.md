# 23种设计模式（C 语言嵌入式视角）

> 本笔记以 GoF 经典 23 种设计模式为骨架，代码统一用 C 编写，场景侧重嵌入式开发（MCU、驱动、RTOS）。示例为教学示意代码，需按目标平台适配。

## 总览：23 种模式一张表

| 分类 | 模式 | 一句话 |
| --- | --- | --- |
| 创建型 | 单例（Singleton） | 全局唯一实例，如唯一的硬件控制器 |
| 创建型 | 工厂方法（Factory Method） | 把"创建哪个产品"的决策下放给具体工厂 |
| 创建型 | 抽象工厂（Abstract Factory） | 创建一族相互关联的产品（平台移植层） |
| 创建型 | 建造者（Builder） | 分步构建复杂对象（复杂外设配置） |
| 创建型 | 原型（Prototype） | 克隆已有对象，避免昂贵重建 |
| 结构型 | 适配器（Adapter） | 接口转换，抹平硬件差异 |
| 结构型 | 桥接（Bridge） | 抽象与实现分离，两个维度独立扩展 |
| 结构型 | 组合（Composite） | 树形结构，统一对待叶子与树枝 |
| 结构型 | 装饰器（Decorator） | 动态叠加功能（协议分层加缓冲/加密） |
| 结构型 | 外观（Facade） | 为复杂子系统提供简化入口 |
| 结构型 | 享元（Flyweight） | 共享内部状态，减少内存占用 |
| 结构型 | 代理（Proxy） | 控制访问（延迟加载、权限保护） |
| 行为型 | 责任链（Chain of Responsibility） | 请求沿处理器链逐级传递 |
| 行为型 | 命令（Command） | 把请求封装成对象，支持排队/撤销 |
| 行为型 | 解释器（Interpreter） | 定义文法并解释（指令解析） |
| 行为型 | 迭代器（Iterator） | 统一方式遍历聚合对象 |
| 行为型 | 中介者（Mediator） | 中央协调，星状取代网状依赖 |
| 行为型 | 备忘录（Memento） | 状态快照与恢复 |
| 行为型 | 观察者（Observer） | 一对多发布订阅（回调/事件） |
| 行为型 | 状态（State） | 内部状态驱动行为（协议状态机） |
| 行为型 | 策略（Strategy） | 算法封装可替换（滤波/校验算法） |
| 行为型 | 模板方法（Template Method） | 固定算法骨架，可变步骤延迟到子类 |
| 行为型 | 访问者（Visitor） | 操作与数据结构分离 |

## 选择指南：遇到什么问题用哪个

- **想要全局唯一的对象**（唯一硬件实例、全局时钟配置）→ 单例
- **想解耦"创建"**：集中判断 → 简单工厂；把决策下放 → 工厂方法；要产品族 → 抽象工厂；要分步配置 → 建造者；创建昂贵 → 原型
- **接口不匹配**（硬件 A 的 API 与系统标准接口不同）→ 适配器
- **两个维度独立变化**（抽象层 × 芯片实现）→ 桥接
- **要给对象动态加功能**（串口上加缓冲层、CRC 层、加密层）→ 装饰器
- **想隐藏复杂子系统**（一键初始化所有外设）→ 外观
- **大量相似对象内存吃紧** → 享元
- **想控制访问/延迟加载** → 代理
- **处理链逐级上报**（异常分级处理）→ 责任链
- **请求要排队/可撤销**（按键命令、协议帧分发）→ 命令
- **要统一遍历**（环形缓冲区遍历）→ 迭代器
- **对象间网状依赖太乱** → 中介者
- **要保存/恢复状态**（参数快照）→ 备忘录
- **一对多通知**（事件分发、回调）→ 观察者
- **对象行为随状态变化**（OTA/协议状态机）→ 状态
- **同一操作多种算法可替换**（滤波、校验）→ 策略
- **流程骨架固定、细节可变**（外设初始化时序）→ 模板方法

## 一、创建型模式：如何优雅地拿到一个对象

这类模式的共同目标是**解耦对象的创建者和使用者**。使用者无需关心对象的具体实现和创建细节，只需通过统一接口获取所需对象。

### 1. 单例模式（Singleton）

- **核心思想**：保证**唯一性**和**全局访问**。一个类在任何情况下都只有一个实例，并提供全局性的 get 方法。
- **关键角色**：私有构造函数（防止外部 new）、静态私有实例、公有静态 `get_instance()`。
- **嵌入式场景**：系统唯一的硬件资源——USART 控制器、时钟配置、看门狗句柄，都只需一个实例。
- **代码示例（修正版双检锁）**：锁必须是**编译期初始化的静态锁**，而不是实例的成员（否则首次加锁时实例尚不存在，会空指针解引用）：

```c
#include <stddef.h>
#include <pthread.h>

typedef struct Singleton
{
    int value;                     /* 实例数据 */
} Singleton;

static Singleton* s_instance = NULL;
static pthread_mutex_t s_lock = PTHREAD_MUTEX_INITIALIZER;   /* 编译期初始化 */

Singleton* get_instance(void)
{
    if (s_instance == NULL)                     /* 快速路径，不加锁 */
    {
        pthread_mutex_lock(&s_lock);
        if (s_instance == NULL)                 /* 加锁后再次检查（双检） */
        {
            s_instance = calloc(1, sizeof(Singleton));
        }
        pthread_mutex_unlock(&s_lock);
    }
    return s_instance;
}
```

> 更简单的做法是用 `pthread_once()` 只初始化一次。C 语言双检锁在无内存屏障保证的平台上仍有隐患，教学示意以单线程环境为前提时可直接去掉锁。

### 2. 工厂方法模式（Factory Method）

- **核心思想**：**推迟实例化**。父类定义一个创建对象的接口，把"实际创建哪种对象"的决定权下放给子类（C 中模拟为函数指针表 / 注册回调）。
- **关键角色**：`Creator`（抽象创建者）、`ConcreteCreator`（具体创建者）、`Product`（产品接口）、`ConcreteProduct`（具体产品）。
- **嵌入式场景**：日志框架的 `LogFactory.createLogger()`——`FileLogFactory` 创建 `FileLogger`，`DatabaseLogFactory` 创建 `DatabaseLogger`，使用者只依赖 `LogFactory`。
- **与简单工厂的区分**：简单工厂是**集中式 switch 判断**（非 GoF 23 种）；工厂方法把判断**下沉到具体工厂**，每个工厂只创建一种产品：

```c
/* 简单工厂：一个函数集中判断 */
typedef enum
{
    DEVICE_UART,
    DEVICE_SPI
} DeviceType;

Device* create_device(DeviceType type)
{
    switch (type)
    {
        case DEVICE_UART:
            return uart_device_create();
        case DEVICE_SPI:
            return spi_device_create();
        default:
            return NULL;
    }
}

/* 工厂方法：创建决定权下放到具体工厂 */
typedef struct DeviceFactory
{
    Device* (*create)(void);        /* 统一的创建接口 */
} DeviceFactory;

static DeviceFactory g_uart_factory = { uart_device_create };
static DeviceFactory g_spi_factory  = { spi_device_create };
```

### 3. 抽象工厂模式（Abstract Factory）

- **核心思想**：创建**产品族**。提供一个接口创建一系列相互关联的对象，是"工厂的工厂"。
- **关键角色**：`AbstractFactory`、`ConcreteFactory`、`AbstractProduct`、`ConcreteProduct`。
- **嵌入式场景**：**平台移植层**——同一套 HAL 接口（GPIO/定时器/串口），不同 MCU 平台用不同工厂实例创建，切换平台只换工厂：

```c
typedef struct Button  { void (*paint)(struct Button* self);  } Button;
typedef struct TextBox { void (*paint)(struct TextBox* self); } TextBox;

typedef struct GUIFactory
{
    Button*  (*create_button)(void);
    TextBox* (*create_textbox)(void);
} GUIFactory;

static const GUIFactory g_windows_factory =
{
    windows_button_create,
    windows_textbox_create
};

static const GUIFactory g_mac_factory =
{
    mac_button_create,
    mac_textbox_create
};
```

### 4. 建造者模式（Builder）

- **核心思想**：**分步构建**。将复杂对象的构建过程与最终表示分离，支持链式调用逐步设置属性，最后 `build()` 生成。
- **关键角色**：`Builder`（构建接口）、`ConcreteBuilder`、`Product`、`Director`（可选，封装固定流程）。
- **嵌入式场景**：配置参数繁多的外设——CAN 过滤器、DMA 通道、串口波特率/校验位/停止位组合。用链式 `.set_baud(115200)->set_parity(NONE)->build()` 避免十几个参数的构造函数。

### 5. 原型模式（Prototype）

- **核心思想**：**克隆**。通过复制已存在的对象（原型）创建新对象，而非重新 new。
- **关键角色**：`Prototype`（含 `clone()`）、`ConcretePrototype`。
- **嵌入式场景**：创建对象代价高（如从 Flash 加载大量默认配置）时，先建一个原型，之后克隆再改少量字段。**深拷贝 / 浅拷贝**是核心注意点。

## 二、结构型模式：如何优雅地组合与拼装

这类模式关注如何把类和对象组合成更大的、更灵活的结构。

### 6. 适配器模式（Adapter）

- **核心思想**：**兼容转换**。像一个转接头，把类的接口转换成客户期望的接口。
- **关键角色**：`Target`（目标接口）、`Adapter`、`Adaptee`（被适配者）。
- **嵌入式场景**：硬件接口差异抹平——把 SPI NOR Flash 的厂商 API 适配成系统统一的块设备接口，上层代码不依赖具体芯片：

```c
/* 目标接口：统一块设备 */
typedef struct BlockDevice
{
    int (*read)(struct BlockDevice* self,
                uint32_t addr, uint8_t* buf, uint32_t len);
} BlockDevice;

/* 适配器：内部调用具体 Flash 厂商 API */
static int spi_flash_block_read(BlockDevice* self,
                                uint32_t addr, uint8_t* buf, uint32_t len)
{
    /* 内部转换为 spi_flash 厂商函数调用 */
    return spi_flash_read(addr, buf, len);
}
```

### 7. 桥接模式（Bridge）

- **核心思想**：**分离抽象与实现**。让两个独立变化维度（抽象概念 × 具体实现）各自独立扩展。
- **关键角色**：`Abstraction`、`RefinedAbstraction`、`Implementor`、`ConcreteImplementor`。
- **嵌入式场景**：形状 × 颜色。不用桥接需 `RedCircle/BlueSquare` 四类；用桥接只需 `Shape` 和 `Color` 两个抽象，`Shape` 持有一个 `Color` 引用，**避免类爆炸**。类比 OS 抽象层与芯片 HAL：上层逻辑绑定抽象接口，底层实现可换。

### 8. 组合模式（Composite）

- **核心思想**：**树形结构**。把对象组合成树，表示"部分-整体"层次，客户统一对待叶子与树枝。
- **关键角色**：`Component`（统一接口）、`Leaf`、`Composite`。
- **嵌入式场景**：GUI 控件树（窗口含按钮、文本框、面板，面板又含控件）、文件系统的目录树、菜单命令树。无论窗口还是按钮都能响应 `draw()`。

### 9. 装饰器模式（Decorator）

- **核心思想**：**动态包装**。不改变对象结构，动态叠加新功能，是继承的灵活替代。
- **关键角色**：`Component`、`ConcreteComponent`、`Decorator`、`ConcreteDecorator`。
- **嵌入式场景**：**协议栈分层**——裸串口字节流上用 `BufferedDecorator` 加缓冲、`CrcDecorator` 加校验、`EncryptDecorator` 加加密，每层只关心自己的增强。和 [[协议分层]] 的"语言与扩音器"思想同构。

### 10. 外观模式（Facade）

- **核心思想**：**简化入口**。为复杂子系统提供统一高层接口。
- **关键角色**：`Facade`、各子系统类。
- **嵌入式场景**：一键初始化——`board_init()` 内部串行完成时钟、GPIO、串口、ADC、看门狗配置，上层只需调用一个函数。家庭影院"一键观影"同理：按下按钮自动关灯、降幕布、开投影。

### 11. 享元模式（Flyweight）

- **核心思想**：**共享复用**。共享内部状态（可共享）以支持大量细粒度对象，外部状态（不可共享）由客户端传入。
- **关键角色**：`Flyweight`、`FlyweightFactory`、内部/外部状态。
- **嵌入式场景**：字符编辑器——每个字符的字形属性是内部状态可共享，位置坐标是外部状态调用时传入；字库/位图模板在嵌入式 Flash 中只存一份。

### 12. 代理模式（Proxy）

- **核心思想**：**控制访问**。为对象提供代理以控制对其访问。
- **关键角色**：`Subject`、`RealSubject`、`Proxy`。
- **嵌入式场景**：图片懒加载（占位图代替高清图，滚动到才真正加载）；寄存器访问保护代理（只有特定上下文可写配置寄存器）；远程代理（CAN 网关转发对远端节点的访问）。

## 三、行为型模式：如何优雅地协作与通信

这类模式专注于对象之间的职责分配和算法封装。

### 13. 责任链模式（Chain of Responsibility）

- **核心思想**：**逐级上报**。把请求的发送者与接收者解耦，处理器串成链，请求沿链传递直到被处理。
- **关键角色**：`Handler`、`ConcreteHandler`、链上的后继指针。
- **嵌入式场景**：采购审批（500 元小组长、5000 元部门经理、以上 CEO）；嵌入式里对应**异常分级处理**、**报文解析链**（先试 ACK 帧、再试数据帧、最后丢弃）。

### 14. 命令模式（Command）

- **核心思想**：**请求封装**。把请求封装成独立对象，支持排队、记录日志、撤销/重做。
- **关键角色**：`Command`、`ConcreteCommand`、`Receiver`、`Invoker`。
- **嵌入式场景**：餐厅点餐（顾客→服务员→订单→后厨）；嵌入式里对应按键命令表、协议帧分发——收到帧即构造命令对象入队，由执行器统一处理，可撤销。

### 15. 解释器模式（Interpreter）

- **核心思想**：**文法解释**。为一种语言定义文法表示和解释器。
- **关键角色**：`AbstractExpression`、`TerminalExpression`、`NonterminalExpression`、`Context`。
- **嵌入式场景**：使用较少，适合自定义语法解析——AT 指令集解析、简易脚本解释器。

### 16. 迭代器模式（Iterator）

- **核心思想**：**统一遍历**。提供统一方法顺序访问聚合对象，不暴露内部表示。
- **关键角色**：`Iterator`、`ConcreteIterator`、`Aggregate`。
- **嵌入式场景**：for-each 的底层实现。对应 [[环形缓冲区]] 的遍历——无论遍历数组、链表还是环形缓冲，对使用者语法一致。

### 17. 中介者模式（Mediator）

- **核心思想**：**中央协调**。用中介对象封装对象间的复杂交互，把网状依赖变成星状。
- **关键角色**：`Mediator`、`Colleague`。
- **嵌入式场景**：飞行塔台（所有飞机只和塔台通信）；嵌入式里对应**模块间通信总线**——各模块只和消息中心交互，避免互相硬依赖。

### 18. 备忘录模式（Memento）

- **核心思想**：**状态快照**。不破坏封装性，捕获并外部保存对象内部状态，以便恢复。
- **关键角色**：`Originator`、`Memento`、`Caretaker`。
- **嵌入式场景**：游戏存档/读档；嵌入式里对应**参数快照**——升级前保存当前配置，升级失败回滚恢复。

### 19. 观察者模式（Observer）

- **核心思想**：**发布-订阅**。定义一对多依赖，发布者状态改变时通知所有订阅者自动更新。
- **关键角色**：`Subject`、`Observer`、`ConcreteSubject`、`ConcreteObserver`。
- **嵌入式场景**：Excel 单元格 B1 订阅 A1（`=A1*2` 自动重算）；嵌入式里就是**回调/事件分发**——驱动事件发布，任务订阅回调，与 [[并发与并行]] 中的回调机制同构：

```c
#include <stddef.h>

typedef void (*EventCallback)(void* user_data, const void* event);

typedef struct Observer
{
    EventCallback callback;
    void* user_data;
    struct Observer* next;
} Observer;

void notify_observers(Observer* head, const void* event)
{
    Observer* cur = head;

    while (cur != NULL)
    {
        cur->callback(cur->user_data, event);
        cur = cur->next;
    }
}
```

### 20. 状态模式（State）

- **核心思想**：**状态驱动行为**。对象内部状态改变时改变其行为，看起来像换了类。
- **关键角色**：`Context`、`State`、`ConcreteState`。
- **嵌入式场景**：在线订单（待支付→已支付→已发货）；嵌入式里就是**协议状态机**——OTA 升级的 IDLE→DOWNLOADING→VERIFYING→UPDATING，每个状态只响应合法的迁移事件：

```c
typedef enum
{
    OTA_IDLE,
    OTA_DOWNLOADING,
    OTA_VERIFYING,
    OTA_UPDATING
} OtaState;

typedef struct OtaContext
{
    OtaState state;
    void (*on_event)(struct OtaContext* self, OtaEvent event);
} OtaContext;

static void idle_on_event(OtaContext* self, OtaEvent event)
{
    /* 只有 DOWNLOAD 事件才迁移到 OTA_DOWNLOADING */
}
```

### 21. 策略模式（Strategy）

- **核心思想**：**算法替换**。封装一系列算法使其可相互替换。
- **关键角色**：`Strategy`、`ConcreteStrategy`、`Context`。
- **嵌入式场景**：电商支付方式切换；嵌入式里就是**驱动算法/校验算法替换**——同一接口下换滤波算法、换校验算法，运行时动态切换：

```c
typedef struct Filter
{
    float (*apply)(struct Filter* self, float sample);
} Filter;

/* 滑动平均滤波 */
static float moving_average_apply(Filter* self, float sample)
{
    /* ... */
}

/* 低通滤波 */
static float low_pass_apply(Filter* self, float sample)
{
    /* ... */
}
```

### 22. 模板方法模式（Template Method）

- **核心思想**：**流程骨架**。在方法中定义算法骨架，把可变步骤延迟到子类。
- **关键角色**：`AbstractClass`（骨架 + 抽象步骤）、`ConcreteClass`。
- **嵌入式场景**：泡茶/泡咖啡（烧水→加料→倒杯→调味）；嵌入式里对应**外设初始化时序**——HAL 库固定"使能时钟→配置寄存器→使能中断"骨架，具体配置延迟到具体外设实现。

### 23. 访问者模式（Visitor）

- **核心思想**：**操作分离**。把数据结构和作用于其上的操作分离，不改变结构即可加新操作。
- **关键角色**：`Visitor`、`ConcreteVisitor`、`Element`、`ObjectStructure`。
- **嵌入式场景**：公司年度汇报（CEO 看 KPI、HR 看工时，各自"访问"所有员工，无需在 Employee 类里堆满方法）；嵌入式里较少用，适用于遍历硬件描述树执行不同操作（统计功耗 / 扫描设备）。

## 易混淆模式辨析

| 易混淆组 | 一句话区分 |
| --- | --- |
| **策略 vs 状态** | 策略：**外部**客户端主动切换算法；状态：**内部**状态自动驱动行为（自己换） |
| **装饰器 vs 代理 vs 适配器** | 适配器=**换接口**；装饰器=**加功能不换接口**；代理=**控制访问**（可只读不增强） |
| **工厂方法 vs 抽象工厂 vs 建造者** | 工厂方法=**单个产品**创建下放；抽象工厂=**产品族**；建造者=**分步构建**复杂对象 |
| **简单工厂 vs 工厂方法** | 简单工厂=集中 switch 判断（非 GoF 23 种）；工厂方法=决策下放子类 |
| **代理 vs 装饰器** | 两者结构几乎一样，差别在意图：代理控制访问，装饰器增强功能 |
