# STM32的启动流程

#### 流程总览图

`[上电/复位]` \-\> `[阶段0: 硬件自举]` \-\> `[阶段1: 内核复位与中断向量表]` \-\> `[阶段2: 链接器脚本蓝图]` \-\> `[阶段3: Reset_Handler]` \-\> `[阶段4: C库初始化]` \-\> `[阶段5: 用户main()]` \-\> `[阶段6: OS接管]` \-\> `[第一个任务运行]`

#### 阶段 0: 硬件自举 \(Bootstrapping\) \- 决策起点

此阶段完全由硬件执行，用于回答最根本的问题：“我的第一条指令在哪？”

1. **检测BOOT引脚**: 芯片复位时，硬件会锁存 `BOOT0` 和 `BOOT1` 引脚的电平状态。

2. **决定启动模式**: 根据引脚电平组合，决定将哪块物理存储器“映射”或“别名”到CPU固定的启动地址空间 `0x00000000`。

    - **`BOOT0 = 0`**** \(常用\)**: **从主闪存 \(Main Flash\) 启动**。Flash的物理地址 `0x08000000` 在逻辑上被映射到 `0x00000000`。这是应用程序正常运行的标准模式。

    - **`BOOT0 = 1, BOOT1 = 0`**: **从系统存储器启动**。ST官方固化的Bootloader被映射，用于ISP串口下载固件。

    - **`BOOT0 = 1, BOOT1 = 1`**: **从嵌入式SRAM启动**。用于高速调试。

*我们后续的讨论全部基于最常用的“从主闪存启动”模式。*

#### 阶段 1: 内核复位与中断向量表 \(Vector Table\) \- 硬件寻址

在确定从Flash启动后，Cortex\-M内核硬件开始执行固定的引导序列，它通过一张“地址地图”——中断向量表，来找到最初的起点。

1. **中断向量表是什么？**
它位于Flash存储器的最顶端（`0x08000000`），是一个由32位地址（函数指针）组成的数组。它就像是操作系统的“紧急联系人”列表，规定了发生任何异常或中断时，CPU应该跳转到哪里去执行代码。

2. **加载主堆栈指针 \(MSP\)**:
CPU首先从 `0x00000000` \(实际访问Flash的`0x08000000`\)读取向量表的**第一个条目**。这个值并非函数地址，而是**主堆栈\(Main Stack\)的初始栈顶地址**。CPU会立即将其加载到 `MSP` 寄存器中。至此，系统最核心的主堆栈已经建立。

3. **加载复位处理函数地址**:
接着，CPU从 `0x00000004` \(实际访问Flash的`0x08000004`\)读取向量表的**第二个条目**。这个值就是 `Reset_Handler` 函数的入口地址。CPU将其加载到 `PC` \(程序计数器\)寄存器中。

4. **跳转执行**:
CPU开始执行 `PC` 指针指向的 `Reset_Handler` 代码。

> **深度解析**: CPU并非凭空知道`Reset_Handler`的存在，而是通过查询这张由硬件规范和软件（链接器）共同确定的向量表来找到它。这张表后续还定义了`NMI_Handler`, `HardFault_Handler`以及各种外设中断（如`USART1_IRQHandler`）的入口地址。虽然向量表默认位于Flash起始位置，但可以通过修改`VTOR`寄存器（Vector Table Offset Register）在运行时将其重定位到RAM或Flash的其他区域，这在实现自定义Bootloader时至关重要。

#### 阶段 2: 链接器脚本 \(Linker Script\) \- 内存布局的蓝图

在 `Reset_Handler` 开始执行之前，我们必须先了解一个“幕后功臣”——链接器脚本（Keil中为`.sct`，GCC中为`.ld`）。它在编译的最后阶段被使用，生成了一份详细的内存“建筑蓝图”，精确地告诉了后续的C库初始化代码，如何构建C语言的运行环境。

- **链接器脚本定义了什么？**

    1. **代码与数据的位置**: 它规定了中断向量表\(`.isr_vector`\)、程序代码\(`.text`\)、只读数据\(`.rodata`\)必须存放在**Flash**中。

    2. **变量的“仓库”与“新家”**: 对于**已初始化的全局/静态变量**\(`.data`段\)，它定义了两个地址：

        - **LMA \(Load Memory Address\)**: 加载内存地址，在**Flash**中。这里存储着这些变量的初始值，就像是存放在“仓库”里的货物。

        - **VMA \(Virtual Memory Address\)**: 虚拟内存地址，在**RAM**中。这是变量在程序运行时真正被读写的位置，就像是货物要被搬去的“新家”。

    3. **待清理的“空地”**: 对于**未初始化或初始化为0的全局/静态变量**\(`.bss`段\)，它只在**RAM**中为其预留了空间（VMA），并记录其大小。这块区域就像是新家里的“待用空地”。

    4. **堆与栈**: 它还定义了堆\(Heap\)和栈\(Stack\)在RAM中的位置和大小。

#### 阶段 3: `Reset_Handler` \- 从汇编到C的桥梁

现在，CPU开始执行`Reset_Handler`。这段汇编代码的任务非常纯粹：根据链接器脚本的规划，为C环境做最后的准备。

1. **基础系统初始化**: 调用 `SystemInit()` C函数。此函数通常完成与C环境无关的最底层硬件配置，如设置系统时钟（PLL、HSI/HSE）和使能FPU（浮点运算单元）。

2. **跳转到C库入口**: 跳转到C运行时库的入口函数 `__main`，正式将控制权交给C的世界。

#### 阶段 4: C运行时库 \(`__main`\) \- 执行内存蓝图

`__main` 函数是C库的一部分，它像一个“搬家公司”，严格按照链接器脚本这张蓝图来施工，搭建起完整的C语言运行环境。

1. **数据段搬运 \(\.data\)**: `__main` 从链接器脚本中读取`.data`段的LMA、VMA和大小。然后，它执行一个`memcpy`类似的操作，将所有已初始化变量的初始值从**Flash \(LMA\)** 精确地复制到**RAM \(VMA\)** 中。 “搬家公司”把货物从仓库搬到了新家。

2. **BSS段清零 \(\.bss\)**: `__main` 读取`.bss`段在RAM中的起始地址和大小，然后执行一个`memset`类似的操作，将这片内存区域全部填充为0。“搬家公司”把新家的空地打扫干净。

完成这两步后，C代码所依赖的所有全局/静态变量都处于正确的初始状态。最后，`__main` 调用我们编写的 `main()` 函数。

#### 阶段 5: 用户代码 \(`main`\) \- 应用逻辑的起点

这是我们最熟悉的部分，应用程序的逻辑从这里开始。

1. **外设初始化**: 调用HAL库或标准库函数，配置GPIO、USART、SPI等硬件外设。

2. **创建OS资源**: 调用 `xTaskCreate()`, `xQueueCreate()` 等API来创建任务、队列等操作系统对象。

3. **启动调度器**: 调用 `vTaskStartScheduler()`。**此函数不会返回**，调用后CPU的控制权将永久性地移交给FreeRTOS内核。

#### 阶段 6: OS接管 \- 多任务时代的开启

`vTaskStartScheduler()` 吹响了多任务系统运行的号角。

1. **配置系统心跳**: 初始化SysTick定时器，作为RTOS的“心跳时钟”。

2. **触发SVC异常**: 选择优先级最高的就绪任务，然后执行 `SVC` 指令，主动请求内核服务，使CPU从**线程模式**进入**处理模式**。

3. **执行****`vPortSVCHandler`**: 在此SVC中断服务函数中，内核加载第一个任务的上下文，并将CPU的堆栈指针从 `MSP` 切换到 **`PSP`**** \(进程堆栈指针\)**，因为每个任务都有自己独立的堆栈。

4. **第一个任务运行**: `vPortSVCHandler` 返回后，CPU自动切换回**线程模式**并使用`PSP`，PC指针指向第一个任务的代码，多任务系统正式开始运行。

5. **后续调度**: 此后，SysTick中断会周期性触发`xPortSysTickHandler`，该函数通过调用`xTaskIncrementTick`来决策是否需要任务切换。若需要，则会触发`PendSV`异常，由`xPortPendSVHandler`完成具体的任务上下文保存与恢复工作。
